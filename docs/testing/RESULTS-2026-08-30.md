## Fixed during the run

### 1. CASC diagnostics on the JSON-RPC stream (A4) — severe

One `get-minimap-tile` call put **28,580 non-protocol lines (1.9 MB)** onto stdout, which is the MCP message channel. Any client calling a minimap tool would have its protocol stream corrupted.

158 `console.log`/`console.error` calls in `src/casc/**` wrote to stdout. All now write to stderr. Re-tested against the real transport with the same minimap call: 10 JSON-RPC responses, **zero** stray lines, 1.8 MB of diagnostics on stderr.

This is the third instance of the same defect — winston's Console transport and the profile-loader banner were the first two — and by far the largest.

### 2. `get-item-info` could not be serialised — severe

Every response containing a real item failed with *"Do not know how to serialize a BigInt"*, over both the MCP transport and the web API. Only the not-found path worked, because it has no item to serialise.

`ItemSparseEntry.allowableRace` was a `BigInt`. JSON cannot carry one at all, and cannot carry 64 bits as a number without losing precision either, so it is now a decimal string.

**Why the earlier checks missed it:** they read properties off the returned object rather than serialising it, and the stdio harness counted JSON-RPC responses without inspecting whether they were errors. Counting responses is not checking them — the harness now needs to assert on content.

### 3. Item detail page showed wrong values (C1.2)

Two bindings read fields that do not exist on the response:

- `item.itemSubclass` — the API returns `itemSubClass`, so every item's subclass rendered as "N/A".
- `item.sellPrice` / `item.buyPrice` / `item.vendorPrice` — prices live on `db2Data.itemSparse`, so every item rendered as costing nothing ("Vendor Price 0 copper").

Item 25 now shows subclass 7, sell 3 copper, buy 18 copper, matching the DB2 file.

### 4. A wrong expectation in the plan itself

`/api/maps/list` returns 11 continent-level maps for the minimap viewer, not the 1,079 maps `mapextractor` produced. The route is right; the plan was wrong and has been corrected.

## Open — needs a decision, not a patch

### 27 of 68 exercised tools accept empty arguments (A2.1)

Tools that declare required parameters but do not enforce them. They fall into three tiers:

**Fabricates data** — the dangerous tier:
- `get-reputation-standing` returns `"currentStanding": "exalted"` for no input at all.

**Causes side effects from empty input:**
- `replay-start-recording` starts a recording session.
- `coordinate-cooldowns` creates a group (`group_1788093875516`).

**Returns `undefined`/`null`-laden output instead of rejecting** (24 tools), including `get-trinity-api` (`class "undefined" not found`), `calculate-melee-damage`, `calculate-armor-mitigation`, `get-talent-build`, `get-leveling-path`, `vmap-test-line-of-sight`, `get-knowledge-node`.

Full list in `test-results-mcp-sectionA.json`.

This is one fix applied 27 times — validate declared-required parameters and return a typed error — but it changes the contract of 27 tools, so it is a decision rather than a mechanical patch.

### Minimap tools start unbounded work on empty input

`get-map-minimap`, `get-minimap-tile` and `get-minimap-tiles-batch` respond to empty arguments by beginning a full CASC encoding-file extraction (~199 MB decompressed). During the first A2 run this exhausted the V8 heap and killed the process after 72 tools. They are recorded as A2 failures and excluded from harness invocation.

### D2 — cold lookup 345 ms against a <100 ms target

The first spell or item lookup in a process loads ~39 MB of JSON caches lazily. Steady state is fine: p95 over 1,000 lookups is **0.01 ms**, with no drift (first-250 avg 0.029 ms, last-250 avg 0.006 ms) and 22.7 MB heap growth over 10,000 lookups.

Either warm the caches at startup, or split the target so cold start is measured separately from p95. The current target conflates them.

## Second pass — fixes and re-run

### Argument validation, fixed centrally

Rather than 27 separate edits, dispatch now validates arguments against the
schema each tool already publishes (`src/tools/registry/validate-args.ts`).
The declared schema became the contract: one implementation covering every
registered tool, including ones added later. Types are checked and never
coerced — a spell id arriving as `"133"` is a caller bug, and coercing it hides
the mismatch until something downstream is wrong.

`get-minimap-tiles-batch` needed a handler check too: it accepts any of three
ways to name its tiles, which `required` cannot express as an either/or, so
empty input still reached the CASC layer. That was what exhausted the heap and
killed the first harness run.

**Re-run:** A2.1 94 PASS / 0 FAIL. All three minimap tools now reject empty
input; `get-reputation-standing`, `replay-start-recording` and
`coordinate-cooldowns` name their missing parameters instead of inventing a
standing, starting a session, or creating a group.

### A per-lookup cost of 190–295 ms, and a flawed measurement

The first pass recorded *"D3 item lookup warm: 0 ms PASS"*. That was wrong: the
test repeated a single id and hit a per-id cache. Measuring distinct ids showed
**144–308 ms on every lookup**, not just the first.

Two causes, both pre-existing:

1. `RecordCache.estimateSize()` recursed with `Object.entries()` over the cached
   `DB2Record`, whose `recordData` is a multi-megabyte Buffer — so it walked one
   entry per byte. Binary data is now measured by `byteLength` and never walked.
   **190–295 ms → 0–1 ms.**
2. `DB2FileLoader.getRecord()` re-read an entire section — every record plus its
   string table — from disk for each lookup. Sections are cached now, cleared on
   reload.

### Cold start

Spell and item caches are warmed shortly after startup, off the request path.
First spell lookup **345 ms → 40 ms**; first item lookup **422 ms → 53 ms**,
subsequent 1 ms. D2 and D3 now pass.

### Web UI re-verification

All routes return correct data (`/api/item/25` Worn Shortsword COMMON ilvl 1;
`/api/item/19019` Thunderfury LEGENDARY ilvl 29; spells 133 and 8326 correct;
999999999 a clean not-found). Pages exercised in a browser: settings (build
panel correct), item detail, spell detail, dashboard, items, creatures — all
render with **no console errors**, and the list pages show proper empty states.

### Third pass — the last two findings closed

**Spell detail now comes from the satellite tables.** `get-spell-info` had been
querying `serverside_spell`, which holds only custom server-side spells, so for
the ~194,000 client spells every gameplay field was zero — indistinguishable
from a genuinely instant, free, rangeless spell. Eight new schemas cover
SpellMisc, SpellCastTimes, SpellDuration, SpellRange, SpellCategories,
SpellCooldowns, SpellLevels and SpellPower. **validate-build-schemas: 17
verified, up from 9.**

Reading them exposed two further defects in the DB2 layer:

- **Narrow accessors ignored compression.** `getUInt8`/`getUInt16`/`getInt8`/
  `getInt16`/`getFloat` read raw bytes at a field offset — correct only for
  uncompressed fields. On SpellMisc four different fields all returned 13632,
  because a bit-packed field has no bytes of its own to read. They now widen
  through the same decode path `getUInt32` used. SpellEffect and ItemSparse
  baselines unchanged.
- **Files with an inline id column were unreadable.** They carry no id list, so
  nothing mapped an id to a position: `SpellPower.db2` reported "searched 0
  sections" for every id. `getRecordByIndex()` reads by position, which is what
  relationship blocks address anyway.

Verified against the game, not against our own output: Fireball Fire / 1750 ms
/ 40 yd / level 10 / 1% base mana; Flash Heal Holy 1500 ms; Arcane Intellect
exactly 3,600,000 ms; Ghost −1 (never expires), Self Only, no power cost.

**Dashboard totals are now labelled** as server-database counts, with a note
that the client data files hold more. Two different questions, no longer looking
like a disagreement.

## Fourth pass — coverage extended to the whole surface

The harnesses previously covered one check (A2.1) on the 68 tools judged safe to
call, and two of the 41 pages. They now cover six checks on all 155 tools and
every page and API route. Extending them turned up five more defects.

### Coverage now

| Area | Before | After |
|------|--------|-------|
| MCP Section A | A2.1 on 68 tools | **831 PASS / 0 FAIL**, six checks over all 155 |
| Side-effecting tools | not exercised | exercised with rejected input; never with satisfiable input |
| Web pages | 2 of 41 in a browser | **41 of 41** requested, 0 failures |
| Web API routes | 12 spot-checked | **37 of 37**, 0 failures |

Dispatch-level validation is what made this safe: a rejected call cannot reach
the code that writes or deletes, so backup, restore and import tools can be
tested for how they refuse bad input without ever being allowed to run.

### Defects found

1. **Two naming conventions for the same settings.** `src/database/connection.ts`
   read only `TRINITY_DB_*`, while the web UI configures itself with `DB_*` and
   imports that module directly — so the pool was built with an empty user and
   every world-database route answered *"Access denied for user ''@'localhost'"*.
   It accepts either name now; `/api/zones` returns 117 zones.

2. **An empty value suppressing a real one.** The web UI passed
   `TRINITY_DB_USER=""` to the MCP child, and dotenv will not override a key
   that is already set — so the empty string stopped the server's own `.env`
   from supplying the user. Only settings with a value are passed down now.

3. **Quest analytics queried columns that do not exist.** `quest_template` has
   none of `QuestLevel`, `MinLevel`, `PrevQuestID`, `NextQuestID`; they live in
   `quest_template_addon`, and it carries `LogTitle`/`RewardBonusMoney` rather
   than `QuestTitle`/`RewardMoney`. Checked against the live schema.

4. **Two of its queries were O(n²).** Each ran a correlated subquery per row
   against a table indexed only on `ID` — ~47,000 quests each scanning ~47,000
   rows. The endpoint took **3.1 minutes** and timed out; as single grouped
   passes it answers in **1.6 seconds**.

5. **Unvalidated input became a filename.** The AI test generator built a
   filename from its source argument. `path.basename()` stopped traversal but
   left quotes and semicolons, so probing it wrote
   `'; DROP TABLE test; --.integration.test.ts` into the repository. Names are
   reduced to safe characters now, and the harness no longer invokes generators.

Also: a missing minimap tile answered 500 where 404 is correct, and `queryWorld`
gained an optional per-query timeout so analytics can exceed the five seconds
sized for point lookups without raising the limit for a stuck one.

### What a harness still cannot see

Honest limits, not excuses:

- **Client-side behaviour** — dark mode, 375 px layout, keyboard traps, focus
  order. The sweep proves each page renders and returns 200; it says nothing
  about how it looks or behaves. That needs a browser, and only six pages have
  been driven in one.
- **Side-effecting tools doing their job.** They are covered for how they refuse
  bad input, not for whether a backup restores. That needs a scratch database.
- **Visual regression** — no baselines exist.

## Fifth pass — the never-run sections, and the browser

Three plan sections had never been executed at all, and the browser gap was
still open. Running them found five more defects.

### B7, B8, A3 — executed for the first time

**B7 exposed a defect on its first assertion.** `search-creatures` failed with
*"Incorrect arguments to mysqld_stmt_execute"*: MySQL's binary protocol will not
accept a placeholder for `LIMIT`, and **ten queries were written that way** —
creature search, item search (twice), spell search (twice), quest chains, quest
routing, table export, and two scaffold templates, so every generated tool
inherited the same broken query. Fixed with `safeLimit()`/`safeOffset()`, which
prove the value is an integer before it is inlined. The scaffold test asserted
the generated code *contained* `LIMIT ?` — it encoded the defect — and now
asserts the opposite.

B7 then passed in full: creature name and faction match the database, search
filters correctly, an absent creature reports not-found, a quest title matches
its row.

**A3 passed as written.** With the database genuinely unreachable a tool throws
in 19 ms with a clear message rather than hanging or returning empty-as-success;
a missing file names the problem; 20 parallel calls return correct, uninterleaved
results in 658 ms.

**B8 corrected the plan rather than the code.** `calculate-armor-mitigation`
returns a percentage, not a fraction — 13.6% at 1,000 armor, 44.1% at 5,000,
75.9% at 20,000, monotonic. The plan's `0 ≤ x < 1` bound was wrong.

### The 4.4 GB, found and returned

The monitoring page — once it stopped inventing its numbers — reported the MCP
child at 98.1% memory. Measured: **one `get-map-minimap` call takes heap from
54 MB to 4,124 MB and it does not come back.** Further calls stay flat, so it is
one-time retention, not a leak per call.

Counted: 2,866,200 index entries, 3,251,498 root entries by path, and the same
3,251,498 again by FileDataID — 9.4 million Map entries. Every index entry also
carried a `Buffer` for a hash **nothing ever read**, each a subarray keeping its
index file alive (~300 MB).

`dispose()` on the readers returns it: **3,575 MB → 9 MB**, re-initialises to
3,579 MB, disposes to 11 MB. Batch extraction releases at its natural boundary;
single-tile extraction keeps the reader, because rebuilding per tile would cost
30 seconds each. `release-casc-memory` gives an operator the same control.

### The dashboard counts instead of inventing

`get-data-distributions` and `/api/distributions` count **410,652 spells across
9 schools, 175,059 items across 9 quality tiers, 222,359 creatures across 16
types**, cached per build — 2.1 s to compute, 1 ms thereafter. Creatures are
grouped by type, not level, and the page says why: they scale to the player, so
`creature_template_difficulty` carries only scaling deltas and there is no fixed
level to bucket by.

That work exposed a manifest bug: the resolver looked module-relative and then
cwd-relative, and **neither works from the web UI** — its working directory is
`web-ui/` and its bundler rewrites `__dirname` — so every server module imported
there fell back to a synthesized manifest reporting **build 0**. It now honours
`MCP_MANIFEST_PATH` and walks up from the working directory.
